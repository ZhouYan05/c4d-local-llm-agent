# 方案设计 —— Local LLM Agent

## 1. 目标

在本机**完全离线**运行一个开源大模型，让它充当 Agent：理解中文自然语言需求，
产出结构化数据，调用本地工具，最终生成一张交互式地图。核心验证点：

1. 模型真的在本地跑（可给出模型名/设备/速度证据）；
2. Agent 真的在做「决策 + 工具调用」，不是把模型输出打印出来；
3. 地图数据**由模型生成**，而非人手写 JSON。

## 2. 整体架构

```
┌──────────────────────────────────────────────────────────┐
│                        CLI / 库 API                        │
│            python -m local_llm_agent.cli generate-map       │
└───────────────────────────┬──────────────────────────────┘
                            │
                  ┌─────────▼─────────┐
                  │     MapAgent      │  多步循环 + trace
                  └─────────┬─────────┘
        ┌───────────────┬───┴────────┬────────────────┐
        ▼               ▼            ▼                ▼
   ┌─────────┐    ┌──────────┐  ┌──────────┐   ┌────────────┐
   │LocalLLM │    │ schemas  │  │  tools   │   │ map_render │
   │ 推理/JSON│    │ 契约/校验 │  │ 函数调用  │   │ Leaflet 渲染│
   └────┬────┘    └──────────┘  └────┬─────┘   └────────────┘
        │                            │
        ▼                            ▼
  Gemma 3 1B (本地权重)      geocode / haversine / validate
```

分层职责：

| 层 | 模块 | 职责 |
| --- | --- | --- |
| 决策 | `llm.py` `agent.py` | 加载权重、采样、把自然语言映射为 JSON 决策 |
| 契约 | `schemas.py` | 定义数据格式与校验器，把"格式正确性"变成可重试的工程问题 |
| 工具 | `tools.py` | 执行副作用：地理编码、坐标校验（模型不直接做副作用） |
| 呈现 | `map_render.py` | 把结构化数据渲染为交互式 HTML |

## 3. 关键设计决策

### 3.1 结构化输出策略（针对小模型）

1B 参数模型一次性生成长 JSON 极易截断/格式错乱。方案：

1. **显式 Schema 提示**：prompt 中给出字段名、类型、取值范围与「只输出 JSON」约束；
2. **宽松解析**：`llm.py` 在文本中定位第一个 `{` 到最后一个 `}`，容忍多余解释文字；
3. **严格校验**：`schemas.py` 的 `validate_*` 检查必填字段、类型、数量区间；
4. **失败重采样**：校验不通过就重新采样，最多 `max_retries` 次（默认 3）。

这把「模型偶发格式错误」变成"可重试、可度量"的工程问题——重试次数也写进 trace，
成为 AI 使用深度的证据。

### 3.2 模型选择

| 模型 | 规模 | 说明 |
| --- | --- | --- |
| **Gemma 3 1B**（主） | 1B | CPU 即可秒级响应，验证门槛低，指令微调版本 JSON 表现良好 |
| Qwen2.5-1.5B-Instruct（备） | 1.5B | 镜像可达性兜底，中文能力强 |

同一份代码只需改 `--model-dir` 即可切换到更大的 Gemma 3 E4B / 26B MoE / 31B，
挑战给出的硬件参考表（E2B/E4B ~5GB，26B MoE ~18GB）均在 31.8GB 内存可承载范围。

### 3.3 坐标合理性

模型生成的经纬度可能漂移。`tools.validate_markers` 用 Haversine 距离过滤：
与中心距离 > 3km 或与已有标记重复的 POI 被剔除并记录原因（trace 中可见）。
这既是幻觉抑制，也让"模型输出 → 可用产物"这一步可度量。

### 3.4 可复现

- 固定随机种子 `seed=20260717`；
- 每个模型调用记录 prompt tokens / new tokens / 耗时 / tok·s⁻¹；
- 完整 trace 落盘为 JSON。

## 4. 数据契约

```jsonc
// Plan
{ "task": str, "place_name": str, "center_lat": num, "center_lon": num,
  "marker_count": int, "categories": [str] }

// MarkerCard
{ "markers": [ { "name": str, "category": str, "description": str,
                 "lat": num, "lon": num } ] }
```

## 5. 运行环境

- 目标机型：i7-14650HX / 31.8GB RAM / RTX 4060 Laptop（8GB）
- Python 3.12、`transformers` + `torch`；CPU 版 torch 亦可运行
- 权重经 `hf-mirror.com` 断点续传下载至 <仓库>/.models

## 6. 非目标 / 后续可扩展

- 不做真实在线地图 POI 抓取（离线地名库 + 模型生成）；
- 后可扩展：接入真实地理编码 API、支持多语言区域、支持更大模型对比评测
  （bonus：uncensored 变体对比）。
